# ADR-0038 · 眼睑开合增益

- 状态：**已实施**（2026-10-31）
- 日期：2026-10-31
- 影响：`params/calibration` 增加 `eyelid_gain`、`web/ipc` 的 eye 段、校准页视线卡片
- 相关：[ADR-0037](0037-calibration-curve-dual-slider-and-labels.md)（形状映射曲线）

## 问题

v2 的眼睑参数是派生值（`params/v2_params.cpp`）：

```text
EyeLidLeft = openness × 0.75 + EyeWideLeft × 0.25
```

模块在正常睁眼时给的 `openness` 是 0.72，到这里只剩 **0.55**。二次元/大眼模型的
正常睁眼往往要 0.7–0.8 才"看起来睁开"，于是用户看到的是眼睛半闭。

而 **`openness` 不在那 88 个形状里**——它是 `EyeState` 的独立字段（模块 IPC 里
两个单独的 float）。校准页的 lo/hi/曲线只作用于 `frame.shapes[88]`，完全够不着它。

用户在眼部四行能调的只有 EyeWide 那 25% 的权重：

- 要把 EyeLid 从 0.55 抬到 0.75，EyeWide 得从 0.042 变成 0.84；
- 校准区间最小跨度 0.02，`lo=0.042 / hi=0.06` 设不出来；
- 曲线也救不了：`t = 0.042` 在任何单调曲线上都接近 0；
- 就算真拉到 0.84，等于"正常睁眼就是最大瞪眼"，之后所有表情都被顶死。

**结论：这是能力缺口，不是用户调法不对。**

## 决策

在 `CalibrationProfile` 加两个参数，作用在 `EyeState.openness` 上：

```cpp
float eyelid_lo   = 0.0f;   // 闭眼时模块报的值（底噪），默认 0
float eyelid_gain = 1.0f;   // 扣掉底噪后再放大，默认 1.0 = 透传
```

`CalibrationApplier::process()` 里，在形状映射之后、视线映射之前：

```cpp
if (profile.eyelid_gain != 1.0f || profile.eyelid_lo > 0.0f) {
    const float lo   = std::clamp(profile.eyelid_lo, 0.0f, 0.5f);
    const float span = 1.0f - lo;
    for (EyeState* eye : {&frame.eyes.left, &frame.eyes.right}) {
        const float base = (eye->openness - lo) / span;
        eye->openness    = clamp01(base * profile.eyelid_gain);
    }
}
```

界面上在校准页「视线」卡片里单独一块：两条滑杆（眼睑增益 0.5–2.5、闭眼基线 0–0.5）、
一个「取闭眼值」按钮，加一行实时预测。档案读取时夹到 0.2–4.0 / 0–0.5。

## 为什么是"先减基线再乘增益"

**只乘增益解决不了闭眼**。实测硬件闭眼时报的 `openness` 是 0.10，不是 0——第一版只有
`gain`，把 0.72 抬到 0.75 的同时也把 0.10 抬成了 0.14，`EyeLid` 留在 0.105，眼睛合不严。
用户是先看到"有效"、再发现"闭不严"的，两个参数缺一不可。

**顺序很关键**：先减基线、按剩余范围归一化，再乘增益。

- 只减不归一化（`(raw - lo) * gain`），lo=0.1 时增益要从 1.6 起算，用户没法把"1.4"和
  观感对上；
- 归一化之后 `gain = 1.0` 依然等于"原样透传"，参数语义从头到尾一致；
- 底噪以下（`raw < lo`，比如闭眼读数抖到 0.08）算出来是负数，被 `clamp01` 收成 0，
  不会出现反向的眼睑。

**为什么不用加法 offset**：offset 会作用在所有表情上，等于给整条曲线加常数，闭眼和正常
睁眼一起平移；而这里要的是"把 0.10 映射成 0"，是缩放加平移的组合，用 lo + gain 表达最直白。

**为什么只有一个 gain、不做曲线**：openness 只有一维，用户要回答的问题就是"再睁开多少"。
真要做"微睁更敏感、大睁饱和"的非线性是下一步的事，成本和收益要另算。

## 为什么不复用形状校准或曲线

- **不复用 lo/hi**：lo/hi 的语义是"这个原始值算 0"，而眼睑的语义是"这个值就是开合度"。
  把 0.72 映射到 0 是错的。
- **暂不做曲线**：openness 只有一维，gain 已经能覆盖"整体再睁大一点"这个需求。
  真要做"微睁时更敏感、大睁时饱和"的非线性，是下一步的事——那需要给 EyeState
  也接一条曲线，成本和收益要另算。

## 与视线校准的关系

`eyelid_gain` 和 `has_eye`（视线校准开关）**互相独立**：

- 只调眼睑不该被迫打开视线校准；
- `dirty` 判定里 `eyelid_gain` 单独比，否则"只调了眼睑"不会提示未保存；
- 档案里同在 `[eye]` 段，但键名分开：

```ini
[eye]
active = 1
gain_x = 1.0000
eyelid_gain = 1.4400
eyelid_lo = 0.1000
```

## 界面

滑杆下方的算式区把两步摊开，用户可以拿计算器验算：

```text
(0.72 − 0.100) ÷ 0.900 × 1.37 = 0.94
EyeLid = 0.94 × 0.75 + EyeWide 0.61 × 0.25 ≈ 0.86
```

分成两行是有意的：第一行是校准层做的事（去底噪、归一化、放大），第二行是 v2 派生层
做的事（0.75 / 0.25 的权重）。合成一行会让人以为"睁眼 0.94 就该是 EyeLid 0.94"。

「取闭眼值」把当前实时预览里的原始 `openness` 填进基线——闭眼时点一下，比让用户猜
一个数字靠谱。它读的是 `PreviewTap` 的校准前值，正是模块此刻报的数。

预测值在**前端**算（抄一份 v2 公式），因为参数页是 10 Hz 低频消息，拖动时等它刷新
会有明显延迟。代价是公式有两处实现，所以这条公式再变时两处都要改——这个风险写在
`update_eyelid_live()` 的注释里。

## 验收

- 单测：增益缩放、零点不变、超 1 夹住、默认透传、**扣基线后闭眼归零**、
  只扣基线不放大、档案 round-trip（两个字段）、只改增益也触发 dirty、手改档案的离谱值被夹。
- 探针：`tools/probe_calibration_ui.py` 断言滑块拿到了 1.37、实时预测有内容。

## 已知取舍

- 增益会让人工睁大更快撞到 1.0。如果模型在 0.9 以上还有形变，可能会觉得"睁到顶就不动了"，
  这时该往回调一点，而不是继续加。
- 基线是**手动抓一次**的静态值。如果模块的闭眼底噪随温度/佩戴漂移（有些摄像头方案会），
  需要隔一段时间重抓一次；做成"运行时自动跟踪最小值"是下一步的事，那会引入
  "用户长时间眯眼被当成闭眼"的新问题。
- 基线只扣不加，所以模块最大睁眼报 0.95 时，`(0.95-0.10)/0.90 = 0.944`，永远差一点点到 1。
  这点差距由增益覆盖，不影响使用。
