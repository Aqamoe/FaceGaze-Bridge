# ADR-0033 · 2D 注视点坐标约定

- 状态：**已实施**（2026-10-31）。**后续**：[ADR-0034](0034-native-module-v2-only.md)
  把位名改为 `FGB_ATTR_LEFT/RIGHT_POINT` 与 `FGB_ATTR_POINT_VIEWPORT`，坐标约定本身不变
- 日期：2026-10-31
- 影响：`sdk/fgb_module_api.h`、`sdk/fgb_shared_frame.h`、`sdk/fgb_udp_frame.h`、
  `src/sources/native_gaze_parse.hpp`、`ui/`（状态页 2D 框）、`docs/05`、`docs/08`
- 关系：收口 [ADR-0030](0030-native-module-v2-composition.md) 的开放问题
  「2D 注视点的坐标约定」；与 [ADR-0026](0026-gaze-estimator-and-api.md) 的逐眼显示配套

## 问题

`FgbGazeV1::left_point_2d` 从落地起就写着「暂定 `[0,1]`、左上原点」，ADR-0030 把
「归一化范围、原点、是否按眼、是否含畸变」留成开放问题。后果是：

- 谁都不敢用。foveation 消费端拿到一个 `[0,1]` 的点，不知道它是"哪块屏幕"的归一化；
- 模块各自猜。有的注视模块用逐眼仿射把原始眼动标定到归一化屏幕上（残差 p95 ≈ 4%），
  有的直接给原始相机/协议坐标，FGB 无法区分这两种；
- 文档与实现都只写"只做透传"，等于把不确定性转嫁给下游。

真机实测（2026-10-31，PICO + 上述模块）：逐眼点在 `0.15–0.98` 之间移动、左右眼稳定
差 3–9% 屏宽，没有出现越界——这与"标定到显示视口"一致，但**没有契约就仍然只是巧合**。

## 决定

### 1. 规范空间 = 该眼的显示视口（需显式声明 `POINT_VIEWPORT`）

```
left_point_2d  / right_point_2d = 该眼视口的归一化坐标
x = 0 左边缘, x = 1 右边缘
y = 0 上边缘, y = 1 下边缘      （原点左上，+x 向右，+y 向下）
```

- **谁的视口**：这一眼最终看到的那块画面（串流/合成的单眼视图），
  不是 HMD 物理面板、不是眼动相机图像、不是桌面显示器。
- **畸变**：坐标在**畸变前**的采样空间里（合成器再套镜头畸变），FGB 不补畸变。
- **单眼独立**：左眼点只在该眼视口内有意义；两眼视口不同（IPD/视锥）时不要互相套用。
- **合并点**：FGB 不产出合并点。需要时消费端取两眼中点，或按需加权。

### 2. 映射责任在模块，FGB 不做几何换算

只有模块知道原始数据的坐标系（相机内参、镜像、换眼、分辨率）。所以：

- 模块负责把原始值映射到上面的视口坐标，再声明 `FGB_GAZE_POINT_2D`；
- FGB **不**做像素→归一化、NDC→`[0,1]`、反投影、四角标定等任何换算。
  拿不到可信映射时不输出点，比输出一个"大概是屏幕"的假点更安全。

### 3. 端点与越界

- `[0,1]` 端点包含在内；
- `0..1` 之外不是错误：视线在视口外、标定误差、边缘回弹都会出现。
  FGB **保留原值**，不裁剪——裁剪会把"看向边框外"伪造成"看向边框"；
- 状态页的 2D 框会 clamp 到框内显示（纯视觉），但 `/api/gaze` 给的是原值；
- 消费端要 clamp 就自己 clamp，并可以据此判断"视线是否出画"。

### 4. 合法性校验

- `NaN` / `Inf`：该眼的点标为无效（`left_point_valid`/`right_point_valid` 为假），
  另一只眼不受影响；
- 声明了 `POINT_VIEWPORT` 却连续 30 帧明显越界（单轴超出 `[-0.25, 1.25]`）：
  宿主日志告警一次，提示"标定错了或空间声明错了"，与「伪造方向」告警同一手法——
  把静默错误变可查。**来源空间的点不参与这个检查**（没有约定范围）；
- 有效性仍然只看 `FGB_GAZE_POINT_2D` 位（与方向位互不连坐，见 ADR-0026 §4.2）。

### 5. 换算公式（给消费端）

```text
NDC（OpenXR / D3D）   x_ndc = 2*x - 1      y_ndc = 1 - 2*y
像素                  px = x * viewport_w  py = y * viewport_h
OpenGL 左下原点 UV     u = x              v = 1 - y
```

`viewport_w/h` 由消费端掌握（它才知道自己在编码/渲染多大），FGB 不猜。

### 6. 空间声明用一位，默认按"来源空间"处理

`FGB_GAZE_POINT_2D` 只表示"有点"，另设一位描述坐标空间：

| 位组合 | 含义 | 能做什么 |
|---|---|---|
| `POINT_2D` | 点在**来源自己的空间**（原始相机/协议坐标，映射未知） | 展示、看两眼差异、做相对趋势；**不能**当屏幕位置用 |
| `POINT_2D \| POINT_VIEWPORT` | 点已标定到本文定义的视口空间 | foveation、注视光标、任何"屏幕上哪儿"的用途 |

- **不写 VIEWPORT 就按来源空间处理**——这是安全默认：`raw` 数据比标定过的常见得多；
- `POINT_VIEWPORT` 是模块的**声明**，FGB 无法验证真伪。所以它只用于"允许消费端更激进地
  使用数据"，而不是"保证数据正确"；凭空声明等于自己承担后果；
- v2 属性帧用帧级属性位 `FGB_ATTR_POINT_VIEWPORT` 表达同一件事；
- 输出面：`/api/gaze` 与 WS JSON 给字符串 `"point_space": "viewport" | "source"`；
  SHM/UDP 在 `gaze_valid` 里加位 `FGB_SHM/UDP_GAZE_POINT_VIEWPORT`（0x10，不改布局）；
  跨进程宿主的 `points_valid` 低两位编码 `VALID|VIEWPORT`（旧读者按 `!=0` 仍然正确）；
- 状态页用两个前缀区分：`2D (x,y)` = 视口坐标，`2D~ (x,y)` = 来源原始坐标。

**为什么最后决定加这一位**（修订，同日）：原本打算只靠"契约 + 越界告警"，
但随后遇到一个只给 **raw per-eye 2D（无标定）** 的模块：实测两眼 x 相差 0.3
（`0.66` vs `0.37`），明显不是视口坐标，而数值又都在 `[0,1]` 内，
**越界告警根本发现不了**。也就是说"不满足契约"的模块会安静地把原始坐标当屏幕点发出去。
这种时候唯一诚实的选择是把"这是什么空间"变成数据的一部分，默认取最保守的那个值。

## 实测证据（2026-10-31，PICO 真机）

标定型来源（模块内部做了逐眼仿射标定）：

```
left_point_2d ∈ [0.15, 0.98]，右眼同区间（多次采样）
左右眼横向差 0.05–0.09（屏宽比例），随视线移动整体平移
越界：未出现；NaN：未出现
```

raw 型来源（同一硬件，模块改回不标定）：

```
left_point_2d ≈ 0.66   right_point_2d ≈ 0.37   —— 两眼 x 相差 0.3
数值仍在 [0,1] 内，但显然不是同一块屏幕上的注视点
/api/gaze 报 point_space="source"，状态页显示 2D~
```

回放（方向型来源）没有点，`point2d_valid=false`，不受本约定影响。

## 不采用的做法

| 做法 | 不用的原因 |
|---|---|
| 像素坐标 | 分辨率随串流码率/窗口变化，同一份数据换机器就失效 |
| NDC `[-1,1]` | 原点在中心、+y 向上，和纹理/UI 约定相反；多一次翻转换算就多一处符号错误 |
| 左下原点 | 图像、D3D 纹理、网页都用左上，翻转没有收益 |
| 物理面板坐标 | foveation 要的是"这一眼看到的画面"，不是面板像素 |
| 带镜头畸变的坐标 | 畸变由合成器施加，FGB 给采样空间才是一段可复用的数据 |
| 由 FGB 反投影成方向 | 需要 FOV/内参/畸变模型，建模前只能编；`dir_local` 与点各走各的通道 |
| 四角标定换算 | 把设备相关工作搬进 FGB，且需要真实标定流程（M7 才可能有） |

## 已知限制

- 模块自报的空间无法被 FGB 验证，只能靠文档 + 越界告警兜底；
- 点是 2D 的，没有深度/世界坐标；与 `dir_local` 不保证在同一坐标系下等价
  （同一模块可能只给其中一种）；
- 两眼的视口差异（IPD/视锥）由消费端处理，FGB 不提供 per-eye transform。
