# ADR-0002 · 眼追默认写 avatar 参数，原生通道作为可选模式

- 状态：已采纳
- 日期：2026-10-28

## 背景

VRChat 有两条接收眼追的路径：

1. **avatar 参数**：`/avatar/parameters/FT/v2/EyeLeftX`、`EyeLidLeft` 等，由 avatar 的
   Animator 消费。VRCFT 走的就是这条，也是 Unified Expressions 规范的实际载体。
2. **原生眼追**：`/tracking/eye/LeftRightPitchYaw`、`/tracking/eye/EyesClosedAmount`，
   由 VRChat 引擎直接驱动眼球，绕过 avatar 的 Animator。

原生通道在纸面上更优：延迟更低、不占 avatar 参数配额、不需要头像作者做绑定。
最初的架构设计因此把它定为默认路径。

## 问题

这个判断忽略了一件事：**生态的实际状态**。

绝大多数现存模型（2022–2024 年制作、以及所有按 VRCFT 教程绑定参数的模型）只在
Animator 里绑了 `FT/v2/*` 参数。切到原生通道后，VRChat 会按自己的逻辑驱动眼球，
avatar 的那套参数绑定完全收不到数据——**眼睛直接不动**。

这不是"效果差一点"，是"看起来完全坏了"。用户不会去看文档理解为什么，只会卸载。

## 决策

**默认 `parameters`，原生通道作为显式可切换模式。**

| 模式 | 行为 | 默认 | 适用 |
|---|---|---|---|
| `parameters` | 眼追写 avatar 参数 | ✅ | 兼容性最好，与 VRCFT 行为完全一致 |
| `native` | 只发 `/tracking/eye/*` | | 明确适配了原生眼追的头像 |
| `both` | 两者都发 | | 调试、过渡期 |

切换入口放在输出页显眼处，并在 UI 上直说"切到 native 后，未适配原生眼追的模型眼睛会不动"。

## 后果

**正面**
- 与 VRCFT 行为一致，老模型零改动可用
- 单一输出路径，调试时不需要考虑两条链路的状态
- 用户的迁移成本为零

**负面**
- 眼追参数（6 个）占用 avatar 参数配额。参数总数从 86 涨到 92
- 需要实现 binary 编码（float 拆 bool）来应对只支持 bool 的头像，这是额外工作量
- 放弃了一部分理论上的延迟收益（实测差异在 1 ms 量级，用户感知不到）

**需要监控**
- 少数头像的 Animator 参数配额确实吃紧，这类用户需要 `native` 模式
- 若未来 VRChat 官方推动原生眼追成为默认，需要重新评估

## 替代方案

**默认 native**：被否决。技术指标更优，但会让大部分用户的第一印象是"这东西是坏的"。
工具的默认行为应该匹配用户已有资产，而不是匹配理论最优。

**只做 parameters，砍掉 native**：被否决。保留 native 的成本很低（约 2 人日），
而它对特定场景（参数配额紧张、明确适配过原生眼追的头像）是唯一解。留一个开关比留一个 issue 便宜。
