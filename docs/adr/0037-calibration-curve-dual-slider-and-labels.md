# ADR-0037 · 校准的三件事：映射曲线、单轨双滑块、形状名称表

- 状态：**已实施**（2026-10-31）
- 日期：2026-10-31
- 影响：`params/calibration` 数据模型与档案格式、`web/ipc` 三条消息、
  `ui/app.js` 校准页重写、新增 `ui/shapes.json`、`docs/09-user-guide.md`

## 问题

ADR-0008 的校准只有 `out = clamp01((raw - lo) / (hi - lo))`，ADR-0021 把它搬进了界面。
用下来暴露三个问题：

1. **一个形状占两行**：lo、hi 各一条滑杆，88 个形状滚不完，而且真正的关键量
   `span = hi - lo`（增益）要用户自己在脑子里做减法。
2. **线性是唯一选择**：真实面捕里"幅度对了但手感不对"极其常见——嘴刚张一点就到 0.5，
   或者中段几乎没有层次。这属于**分配**问题，调 lo/hi 治不了。
3. **协议名看不懂**：`MouthCornerSlantLeft` 对非开发者没有意义，而它恰恰是最需要
   逐个调的东西。

## 决策

### 一、曲线作用在归一化后的 t 上，两端锚死

```text
t   = clamp01((raw - lo) / (hi - lo))
out = curve(t)
```

`curve(0) = 0`、`curve(1) = 1` 是硬约束（`sanitize_curve` 强制改写端点）。

理由：lo/hi 回答"哪里算 0、哪里算 1"，曲线只回答"中间怎么分配"。两件事必须正交，
否则用户会拿曲线去干 lo/hi 的活，越调越乱；而端点一旦自由，就会出现"最高只到 0.8"
这种用户没有任何线索能解释的状态。

预设：`linear`、`ease_in`（t²，压住小动作）、`ease_out`（1-(1-t)²，轻动作就明显）、
`smooth`（smoothstep，中段最灵敏）、`step`（过阈值即到位，带 0.02 过渡带）。

### 二、自定义曲线是单调三次 Hermite，不是折线

8 个控制点上限，按 x 升序。求值用 Fritsch–Carlson 单调保形切线（monotone cubic Hermite）：
每段切线由相邻割线加权，再做"切线不超过割线 3 倍"的修正，最后用 Hermite 基函数求值。

- **为什么不是折线**：这是面捕表情的映射，输出必须连续。折线在每个控制点处有折角，
  放大到脸上就是"一顿一顿"。第一版实现（当天上午）用了折线，被实际观感当场否掉。
- **为什么不是普通样条**：Catmull-Rom / 自然三次样条会**过冲**——曲线可能冲出相邻控制点
  的范围，甚至局部反向，表情就会抽。单调保形版本在数学上排除了这种可能。
- **为什么不需要缓存切线**：控制点 ≤8，每帧重算一遍切线约 30 次浮点运算；88 形状 × 120 Hz
  也只有几十万次/秒。**刻意不缓存**——缓存意味着 `points` 和 `tangents` 两份数据，
  迟早出现"点动了切线没动"，而那种 bug 只会表现为"某些形状的手感莫名其妙"。
- 端点切线取单侧割线，配合端点锚定 `(0,0)/(1,1)`，曲线在两端不会翘出去。

单测直接钉住三条性质：穿过控制点、单调且不过冲、控制点两侧斜率连续
（折线在这里会从 1.8 直接掉到 0.2，这正是"一段一段"的来源）。

### 三、曲线按槽去重，不内联进 ShapeRange

`CalibrationProfile` 里新增 `std::array<CurveShape, 8> custom_curves`，`ShapeRange`
只多两个字段：`curve`（uint8，预设 id 或 `kCurveCustomBase + 槽号`）和 `curve_param`
（step 阈值）。

这直接关系到 seqlock：`CalibrationApplier` 的整套设计前提是"档案是 POD、按值拷贝比加锁
便宜"（见 `calibration.hpp` 的注释）。如果把 8 个控制点内联进 88 个 ShapeRange，
档案会从约 2 KB 涨到 7 KB 以上，每次拖滑杆的拷贝成本就要重新算账。用槽位表之后，
88 × 16 B + 8 × 68 B ≈ 2 KB，前提仍然成立，而且多个形状可以共享同一条曲线
（左右脸用两条不同的自定义曲线几乎没有正当理由）。

不做的方案：LUT 预编译。Hermite 求值本来就够快，LUT 会再把档案撑大十几倍——省下的那点
算术远不如拷贝成本重要。

### 四、档案格式向后兼容

```ini
[shapes]
JawOpen = 0.1200 0.8800 smooth
MouthCornerPullLeft = 0.0500 0.8500 custom:1
MouthPressRight = 0.3000 0.7000 step 0.4200

[curves]
1 = 0.000,0.000 0.300,0.550 1.000,1.000
```

第三段缺省即 `linear`——旧档案只有两个数，读进来行为不变，升级不改手感。
`[curves]` 只写被引用的槽，空槽不写（写了会让人以为它生效）。
曲线 id 用文字不用数字：档案是给人手改的，`custom:1` 比 `9` 好读得多，认不出来的
一律退回 `linear`。

### 五、双滑块：自绘 + 碰撞阻挡

一条轨道两个拇指，两端各一个数字输入框，轨道中间那段填充直接就是 `span`。

- 不用两个 `input[type=range]` 叠层：那样做不出"拖中间段整体平移"，而平移是这个界面
  最常用的动作（调完 lo 往往要同步移 hi）。
- `lo > hi` 的旧行为是**交换两端**（`ipc.cpp`）。在双滑块上这等于两个拇指在手指底下
  瞬间对调，完全没法继续控制。改成**碰撞阻挡**：拖到贴住就停住，松手后还能往回拖，
  间距下限 `kMinSpan = 0.02`。
- 阈值统一：`calibration.cpp` 原来用 `kMinSpan = 0.05` 判定"是否启用"，而 IPC 的
  `capture_calibration` / `set_calibration_shape` 用 0.02，导致"界面里启用了、跨度 0.030、
  保存重载后变未激活"。现在拆成两个有名字的常量：`kMinSpan = 0.02`（能不能用）、
  `kMinDeriveSpan = 0.05`（这段数据值不值得推导）。这是本次顺带修掉的真实缺陷。
- 键盘可达性不能丢：拇指是 `role="slider"` + `tabindex`，方向键 0.005，Shift 0.05。
- 拖动或手填数值时自动勾选启用——用户开始调这个形状，就是想让它生效。

### 六、形状名称走独立数据文件

新增 `ui/shapes.json`：协议名 → `{zh, en, group, tip}`，88 条全覆盖，9 个分组。

- 不塞 `i18n.js`：那里已经 90 KB 以上，而且翻译文件不该承载领域映射。
- 不塞 `face_map.json`：那是模型资产（"这个参数在模型上动哪里"），换模型时不该动名字。
  两份数据的分工是：`shapes.json` 说"这个参数是什么"，`face_map.json` 说"它动哪里"。
- 命名结构是 `部位 + 动作 (+ 一句话说明)`，例如「右眼 眯眼 / 眼周收紧、下眼睑上抬」。
- 搜索必须同时匹配中文名、英文名、说明和协议名（`cal_apply_filter` 的 haystack），
  否则中文用户搜"眯眼"搜不到，名称表等于白加。

## 已知取舍

- 自定义曲线最多 8 条、每条 8 点。超了复用槽 0，界面上不阻止（八条曲线还不够用的场景，
  问题多半不在曲线）。
- 曲线会改变噪声放大的倍数：陡峭段（斜率 > 3）会把传感器抖动放大成可见抖动。
  界面目前没有斜率提示，只有浮层里的实时游标。后续可以在缩略图上标最大斜率。
- 左右镜像（"同步到另一侧"）只在浮层里提供，没有批量操作；88 个形状逐个点仍然繁琐。
