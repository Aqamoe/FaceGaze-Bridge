> 估算单位为**人日**（1 人日 ≈ 6 小时有效工作），按"有 C++ 经验、不熟 VR 生态"的开发者估算。

## M0 · 技术预研（10–14 人日）

**唯一目标：验证 5 个架构假设。任一证伪，回炉改架构。**

这一段写的代码全部是可丢弃的 spike，不进产品分支。

### 假设 1：能在不安装 VRCFT 的机器上驱动 `ModuleProcess.exe`

| 项 | 内容 |
|---|---|
| 验证方法 | 拷贝 `ModuleProcess.exe` + `VRCFaceTracking.Core.dll` + `VRCFaceTracking.SDK.dll` 到干净目录，用 `CreateProcess` 带 `--port/--module` 启动，尝试握手 |
| 关键未知 | 启动参数的确切形式与顺序；是否检查安装路径；是否有额外的运行时依赖（VC++ 运行库、WebView2） |
| 通过标准 | 收到 `HandshakePacket`，完成 init，收到 5 秒连续 `ReplyUpdatePacket` |
| 失败兜底 | 改为"要求用户安装 VRCFT 并复用其目录"，功能不减，但分发体验变差 |

### 假设 2：能正确解码 `ReplyUpdatePacket`（含分片重组）

| 项 | 内容 |
|---|---|
| 验证方法 | Wireshark 抓回环 UDP + 对照 VRCFT 源码结构推断字段布局；构造 3 种不同模块（眼追 only / 表情 only / 双支持）对比 |
| 关键未知 | 字段序、浮点精度（float/double）、形状数组长度是否随版本变化、分片头格式 |
| 通过标准 | 解码出的 `JawOpen` / `EyeLidLeft` 数值与 VRCFT 官方 UI 显示一致（误差 < 1e-4） |
| 失败兜底 | 改用"自带一个改造版 ModuleProcess"（Apache-2.0 允许 fork），协议自定义，但兼容性靠 fork 维护 |

> ⚠️ 这是整个项目**最大的技术风险点**。M0 花一半时间在它上面是值得的。

### 假设 3：VRChat 原生眼追通道可用且优于 avatar 参数

| 项 | 内容 |
|---|---|
| 验证方法 | 写 200 行 Python 脚本，向 `:9000` 发 `/tracking/eye/LeftRightPitchYaw` 与 `EyesClosedAmount`，观察 VRChat 内头像反应 |
| 关键未知 | 是否需要 avatar 侧开启什么；与 VRCFT 参数是否冲突；实际延迟差异 |
| 通过标准 | 眼睛跟随、眨眼正常；与参数驱动相比延迟不劣化 |
| 失败兜底 | 回退到纯 avatar 参数路径（功能不减，参数占用变多） |

### 假设 4：OSCQuery 参数裁剪能显著降低开销

| 项 | 内容 |
|---|---|
| 验证方法 | 对比"全量发 130 参数 @ 90 Hz" vs "只发 avatar 实际存在的 40 个" 的 VRChat 帧时间与网络包量 |
| 通过标准 | 裁剪后 VRChat 帧时间改善 > 3%，或包量下降 > 60% |
| 失败兜底 | 仍做裁剪（无害），但降低优先级 |

### 假设 5：WebView2 + C++ 后端方案可用

| 项 | 内容 |
|---|---|
| 验证方法 | 最小 demo：C++ 起 HTTP+WS 服务，WebView2 加载本地页面，实时画 120 个参数条 |
| 关键未知 | 200% DPI 下的清晰度；无网络环境的运行时可用性；启动耗时 |
| 通过标准 | 冷启动 < 1.5 s，内存 < 90 MB，DPI 无模糊 |
| 失败兜底 | 换 Dear ImGui（丑但快）或 Qt（重但稳） |

### M0 产出物

- `spike/` 目录下 5 个可丢弃程序
- 一份 `docs/adr/0001-protocol-findings.md`：协议字段表（这是后续所有工作的地基）
- 结论：**继续 / 调整架构 / 放弃**

### 验收标准

- [ ] VSeeFace 输出 VMC → FGB → VRChat 头像表情跟随
- [ ] `fgb-cli diag latency` 显示软件侧 P99 < 3 ms
- [ ] 连续运行 1 小时无崩溃、无内存增长
- [ ] OSC 编码吞吐 > 500k msg/s（单核）
- [ ] CI 绿灯（含单测 + 静态分析）

### 为什么先做 VMC 而不是 VRCFT 兼容

VMC 协议简单、可控、无需逆向，能在 2 天内拿到真实数据跑通全链路。**先用简单源验证管道，再接复杂源**——顺序反了会在调试时无法区分"是管道错还是协议解析错"。

## M7 · 校准工作台与桌面集成（P2，22–39 人日，v1.0 之后）

**目标：把"校准"从命令行档案变成看得见的操作；补上托盘常驻；让 FGB 能跟随 SteamVR 启动。**
三项都不阻塞 v1.0，按用户反馈决定先后。已确认的顺序是：**先做托盘（M7.0），
再做 SteamVR 自启动（M7.2）**；校准工作台可并行或先做数据链路。

评估与取舍见 [ADR-0020](adr/0020-steamvr-autostart.md)、
[ADR-0021](adr/0021-calibration-workbench-3d-preview.md)。

**验收（实测通过，Windows 10 22H2）**：

- [x] `FaceGaze Bridge.exe --tray` 启动后无窗口、托盘有图标、引擎在跑
      （额外验证：`msedgewebview2` 进程数为 0，窗口第一次打开才创建）
- [x] 托盘菜单能恢复窗口、停止引擎、重启引擎、退出；退出后无残留进程

- [x] 关闭窗口的行为有明确文档（收进托盘；托盘「退出」才停引擎）
- [x] 资源管理器重启（`TaskbarCreated`）后图标会重新加回

## 建议的第一个动作

不要从 M0 开始写代码。先做这两件事（各半天）：

1. **装 VRCFT，用一个真实模块，把 VRChat 跑起来**——建立"正确是什么样"的基准感知
2. **用 Wireshark 抓 30 秒 VRCFT 与 ModuleProcess 的 UDP 流量**——看一眼真实协议长什么样

有了这两个直觉，M0 的验证效率会高一倍。
